# Tipi CMS : développement d'extensions V0.6

Lire cms_site_info, cg_capabilities et ce guide. Le profil Création de fonctionnalités et les scopes OAuth codegraft:read/write sont nécessaires. Ne modifiez jamais le noyau, la passerelle, le coffre, les contenus privés ou le serveur. Utilisez cg_list_files / cg_read_files, puis cg_prepare_patch ou cg_prepare_diff et cg_validate_patch. Appelez cg_review_release(id, operation=deploy) et utilisez son empreinte exacte. Lisez approval_mode dans cms_site_info : cms = validation dans /admin?connections=1 ; chat = présenter les fichiers, effets et risques, demander une validation explicite dans la conversation et attendre la réponse, puis cg_deploy_patch(id,fingerprint) ; auto = déployer dans le cadre de la demande autorisée, sous réserve des confirmations imposées par le client. Aucun outil ne permet de changer le mode : seul le propriétaire authentifié le choisit. Pas de commande système. Les modes chat et auto délèguent le déploiement au client OAuth ; le serveur ne reçoit pas de preuve humaine de confirmation. Chaque fichier doit être approuvé par son empreinte ; le PHP approuvé s'exécute avec les droits du compte.

## Fichiers autorisés (un niveau par dossier)
- app/McpActions/Nom.php : retourne une fonction (CGF\ActionRegistry $registry, TipiBusinessContext $context): void. register(nom, description, mode read/write, schéma JSON, handler, autorisation optionnelle). Nom snake_case, 2-51 caractères. Les actions deviennent app_nom ; cg_app_catalog et cg_app_invoke les découvrent sans rafraîchir le client. $context->database('nom') retourne CGF\Database (SQLite privé, lazy), $context->service('Nom') charge un service approuvé. SQL préparé, schémas et validations obligatoires. Pas de création de base à la découverte.
- app/Routes/nom.json : {"path":"/admin/apps/nom","title":"Mon outil","handler":"app/Controllers/Nom.php","post":true,"menu":true}. Les routes privées /admin/apps/nom requièrent la session administrateur. Les routes publiques /apps/nom sont explicitement publiques ; GET par défaut, POST uniquement si post=true et CSRF valide. Pas de route arbitraire sur /admin, /mcp, /api. menu ajoute automatiquement une entrée dans le menu approprié.
- app/Controllers/Nom.php : retourne une fonction (TipiWebContext $ctx,array $query,array $post): string. $ctx->method, $ctx->path, $ctx->owner ; $ctx->action('nom',args) exécute les mêmes actions métier qu'en MCP, réservées aux routes privées, écritures POST seulement. $ctx->view('Nom',vars), $ctx->service('Nom'), $ctx->database('nom') (usage PHP de confiance, ne jamais exposer de données privées sur les routes publiques), $ctx->csrf() dans les formulaires. redirect($ctx->path) après POST.
- app/Views/Nom.php : template PHP exécuté avec $vars, $ctx ; échapper toute donnée via e(). Ne jamais injecter de HTML provenant d'un visiteur. app/Services/Nom.php et app/Components/Nom.php : code de confiance retournant une fonction ou un service ; chargement des services via service(), composants PHP via vue/service ou inclusion explicitement validée.
- themes/layouts/site.html : layout global, contient obligatoirement {{head}} (SEO, CSS et scripts) et {{content}}, facultatifs {{brand}}, {{navigation}}, {{title}}, {{credit}}, {{component:nom}}. Exemple <!doctype html><html lang="fr"><head>{{head}}</head><body><header>{{brand}}<nav>{{navigation}}</nav></header><main>{{content}}</main><footer>{{credit}}</footer></body></html>.
- themes/templates/nom.html : enveloppe du contenu, contient {{content}} et facultatif {{title}}. Sélectionner avec template: nom dans front matter Markdown.
- themes/components/nom.html : fragment HTML réutilisable via {{component:nom}} dans le layout ou seul sur une ligne Markdown. Ne pas insérer de secrets.
- assets/css/nom.css et assets/js/nom.js : ressources approuvées, chargées automatiquement sur les pages publiques, pas sur l'administration ou prévisualisation privée. Le CSP interdit scripts inline et distants ; utiliser addEventListener, classes, CSS @keyframes et prefers-reduced-motion. Ne pas utiliser de tracking externe sans accord. Les ressources sont servies par le CMS depuis un dossier hors public.
- Le module Contacts fourni combine app/McpActions/Contacts.php, app/Controllers/Contacts.php, app/Views/Contacts.php et app/Routes/contacts.json. La vue privée et MCP utilisent les mêmes actions.

## Après déploiement
Vérifier le rendu et les actions ; les extensions modifiées hors du circuit d'approbation sont ignorées. Le rollback se prépare avec cg_review_release(id,operation=rollback), puis cg_rollback_patch(id,fingerprint) selon le même mode de validation. Il restaure le code, réactive uniquement les versions déjà approuvées enregistrées au déploiement et ne restaure pas SQLite. Les migrations de schéma sont à concevoir explicitement avec sauvegarde et compatibilité ; aucun SQL générique exposé. Ce n'est pas une sandbox : ne pas exécuter de PHP ou JavaScript non fiable. Le CMS et le compte hébergeur doivent être isolés des autres clients.

## Nettoyage V0.7
Pour les contenus, utiliser cms_list_pages et state_sha256 (empreinte des versions publiée et brouillon), puis cms_delete_page ou cms_delete_pages (1 à 100 documents). Demander l'accord explicite avant suppression, y compris en mode autonome. cms_list_trash et cms_restore_page restaurent une révision lorsque le slug est libre. Pour retirer les extensions, utiliser cg_prepare_delete avec chemins autorisés et expected_sha256, vérifier les dépendances, puis cg_review_release et cg_deploy_patch selon le mode de validation. Ne pas supprimer le noyau, les données SQLite ou les secrets. Le rollback de suppression restaure les fichiers et leurs approbations antérieures. Pour remettre à zéro le design, utiliser cms_update_design et les outils de suppression des extensions de thème. Aucune commande de reset global irréversible.


## Mesure d’audience et événements métier V0.8
Appeler cms_tracking_info pour connaître les services et le contrat disponibles, sans lire de clé. Ne jamais ajouter soi-même tracker.js ou optimize.js, ni modifier le consentement. Le noyau injecte ces scripts sur les pages publiques, même après changement du layout. Aucun tracking dans l'administration, les aperçus ou MCP.
- Pour un clic simple, utiliser le contrat Trackers V2 déjà supporté par Analytics : `<a href="/guide" data-ta-event="guide_clicked" data-ta-revenue="0.50" data-ta-revenue-kind="estimated" data-ta-meta-slot="article">Lire le guide</a>`. Ne pas dupliquer ce clic avec JavaScript. Un événement ne représente pas un paiement réel.
- Pour une interaction JS spécifique, par exemple une simulation achevée : `window.Tipi?.track('simulation_completed', {service:'creation-site'});`. Ne pas ajouter une seconde capture du même événement dans le HTML ou les règles Hub. Les noms métier doivent rester stables lorsque le design évolue.
- Après une action réussie dans le contrôleur POST d'une route publique /apps/ (validation, écriture SQLite terminée), appeler `Tipi::track('quote_requested', ['service'=>'creation-site'], 'quote:'.$id);`. La référence métier stable est hachée pour l'identifiant de collecte. Le SDK n'envoie ni formulaire ni données personnelles en clair ; transmettre uniquement des dimensions non personnelles. Sans consentement et identifiant visiteur Analytics, l'appel est ignoré. Aucun événement de succès sur simple clic ou soumission non validée. Les actions MCP et les routes privées n'alimentent pas les statistiques visiteurs. L'envoi est tenté à la fin de la requête, avec file locale bornée, délai court et possibilité de relance. Un retour true signifie mise en file, pas réception confirmée par le Hub.
- Pour les tests A/B, utiliser des identifiants HTML stables tels que `data-tipi-element="main_cta"` (convention de développement, pas une intégration de sélection Optimize garantie). Conserver les identifiants et événements lors des refontes. Éviter un registre d'événements obligatoire : les événements existants sont collectés par le tracker.
- Les paiements réels ne sont pas implémentés par ce SDK : ils devront utiliser la voie serveur authentifiée /api/revenue/events après vérification du paiement. Pas de clé de revenus exposée dans le navigateur. Association native au Hub, Hector, Mailing et inventaire SEO restent à raccorder côté écosystème.
